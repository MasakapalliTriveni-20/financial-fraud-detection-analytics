## 🏛️ 1. Architecture & Distributed Execution Foundations

### 1.1 Why Apache Spark for Financial Fraud Detection?
Financial transaction systems process millions of events per second (e.g., ATM withdrawals, USSD mobile banking, POS transactions, SWIFT bank transfers). Traditional relational database management systems (RDBMS) suffer from lock contention, disk I/O bottlenecks, and lack horizontal scaling.

Apache Spark solves this through:
1. **In-Memory Computation**: Spark stores intermediate resilient distributed datasets (RDDs) and DataFrames in memory (RAM) rather than writing to disk between execution stages, delivering 10x–100x higher throughput than classic Hadoop MapReduce.
2. **Directed Acyclic Graph (DAG) Execution Engine**: Optimizes stage boundaries, pipelining transformations (e.g., map, filter) into single execution stages to eliminate unnecessary data shuffling.
3. **Catalyst Optimizer**: Translates declarative Spark SQL queries into optimized physical query plans (pushing down predicates, pruning unused columns, and choosing optimal join algorithms).
4. **PySpark MLlib Pipelines**: Standardizes feature transformation (`StringIndexer`, `VectorAssembler`, `StandardScaler`) and distributed model training (`RandomForestClassifier`, `GBTClassifier`) across cluster workers.

## 📁 2. Hadoop & Distributed Storage Architecture

### 2.1 The Distributed Storage Anatomy (`results/parquet/partitioned_transactions/`)
When Spark executes `df.write.partitionBy("payment_channel").parquet(...)`, it generates a directory structure adhering to Hadoop Distributed File System (HDFS) conventions:

```
results/parquet/partitioned_transactions/
├── _SUCCESS
├── ._SUCCESS.crc
├── payment_channel=Bank Transfer/
│   ├── part-00000-c000.snappy.parquet
│   └── .part-00000-c000.snappy.parquet.crc
├── payment_channel=Card/
│   └── part-00001-c000.snappy.parquet
├── payment_channel=Mobile App/
│   └── part-00002-c000.snappy.parquet
└── payment_channel=USSD/
    └── part-00003-c000.snappy.parquet
```

### 2.2 Deep Dive into File Artifacts (Crucial Viva Concepts)
* **`_SUCCESS`**: A 0-byte marker file generated by the Hadoop `FileOutputCommitter`. Its presence guarantees that all tasks in the Spark distributed job finished without failure. If a job crashes midway, `_SUCCESS` is never written, preventing downstream consumers from reading partial/corrupt data.
* **`part-XXXXX-*.parquet`**: The actual columnar data payload written by worker task `XXXXX`.
* **`.crc` (Cyclic Redundancy Check)**: Checksum files used by HDFS and local file systems to detect bit rot and data corruption during distributed network transfer.
* **Partition Pruning**: When a query filters by `WHERE payment_channel = 'USSD'`, Spark skips reading the directories for `Card`, `Mobile App`, and `Bank Transfer`, reducing disk I/O by 75%.

## ⚙️ 3. Machine Learning Foundations & Class Imbalance

### 3.1 The Extreme Class Imbalance Challenge
* In real-world enterprise banking, legitimate transactions vastly outnumber fraudulent ones:
  * **Legitimate (Class 0):** 96.39%
  * **Fraudulent (Class 1):** 3.61%
  * **Imbalance Ratio:** ~26.7 : 1
* **Why Traditional Accuracy is Deceptive**: A naive classifier that predicts *every* transaction as legitimate achieves **96.39% accuracy**, yet fails to detect a single fraud event.
* **Resolution**:
  1. **Cost-Sensitive Weighting**: Weighting the minority fraud class during loss optimization (`loss_weight = 26.0`).
  2. **Balanced Stratified Sampling**: Ensuring tree splits evaluate purity across both classes.
  3. **Multi-Metric Evaluation**: Prioritizing **Precision**, **Recall**, **F1-Score**, and **Area Under ROC (ROC-AUC)** rather than raw accuracy.

## 🎯 4. Viva Examination Preparation: Key Questions & Model Answers

### Q1: What is the difference between RDD, DataFrame, and Dataset in Apache Spark?
* **RDD (Resilient Distributed Dataset)**: Spark’s foundational low-level abstraction. Immutable, fault-tolerant collection of objects distributed across nodes. Does not have schema awareness and lacks Catalyst query optimization.
* **DataFrame**: Distributed collection of data organized into named columns (conceptually equivalent to a relational table). Benefits from Catalyst optimization and Tungsten off-heap memory management.
* **Dataset**: Strongly typed API available in Scala/Java combining RDD type safety with DataFrame performance optimizations. In Python (dynamically typed), DataFrame and Dataset APIs are unified.

### Q2: What is the role of VectorAssembler in PySpark MLlib?
* Machine learning algorithms in PySpark MLlib require all input features to be consolidated into a single vector column (e.g., `features: Vector`).
* `VectorAssembler` is a feature transformer that accepts a list of numerical and indexed categorical columns and merges them into a single dense/sparse feature vector row-by-row in a distributed fashion.

### Q3: How does Isolation Forest differ from Random Forest?
* **Random Forest** is a *supervised* ensemble algorithm that builds multiple decision trees using labeled ground truth (`is_fraud = 0 or 1`) to classify inputs.
* **Isolation Forest** is an *unsupervised* anomaly detection algorithm. It isolates anomalies by randomly selecting a feature and randomly selecting a split value. Because anomalies are few and structurally distinct, they require fewer random partition splits to isolate, resulting in significantly shorter path lengths in the isolation trees.

### Q4: What is data shuffling in Spark and why is it expensive?
* Data shuffling is the physical redistribution of data across cluster partitions/nodes, triggered by wide transformations like `groupByKey`, `reduceByKey`, `join`, and `partitionBy`.
* It is computationally expensive because it involves serializing data, writing to disk, transmitting across the network to other worker nodes, and deserializing.

### Q5: What is the purpose of the unified threat scoring engine in this project?
* Supervised models (Random Forest) excel at detecting *known* fraud patterns previously observed in training logs.
* Unsupervised models (Isolation Forest) excel at detecting *novel / zero-day* anomalies and unprecedented transaction surges.
* The unified engine correlates both outputs to categorize transactions into 4 risk tiers (`CRITICAL`, `HIGH`, `SUSPICIOUS`, `LEGITIMATE`), minimizing false positives while preventing catastrophic zero-day financial loss.
